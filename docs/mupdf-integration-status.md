# MuPDF integration: status

Last updated 2026-09-16. Branch `master`, starting commit `aac2d70`.

This file exists so nobody has to guess which parts of the integration are real.
Nothing here is described as working because it compiles.

## Implemented and tested

`npm run test:mupdf` — 23 cases, 77 assertions, against the real
`fixtures/output/comic.pdf` and `comic.epub`.

| Capability | Evidence |

| Search with cancellation | `search honours its cancellation token` |
| Executor: promises always settle, teardown with work in flight | four cases |

### Texture cache

`npm run test:ts` — 15 cases in `src/renderer/__tests__/PageTextureCache.test.ts`.

Nine-field cache identity, LRU eviction against a byte budget, retain/release
so eviction never disposes a texture the current frame is sampling, invalidation
on document or layout change, and the duplicate-insert race. A double dispose
fails the test rather than being tolerated.

### Nitro layer

`MuPDFFactory` (autolinked root) → `MuPDFDocument` → `RenderedPage`, generated by
Nitrogen 0.37.1 and implemented in C++ for both platforms. All three compile
against the generated specs; `tsc --noEmit` is clean.

## Implemented, not yet proven

- **Outline, page text, search** run without error, but the fixtures are
  generated comic pages. They need a real text-bearing PDF and a long-form EPUB
  before any claim about quality.
- **Password handling.** Written, and the classifier is mapped against the real
  1.28.4 error enum. No password-protected fixture yet, so untested.
- **The renderer cache in situ.** `PageTextureCache` is tested on its own and
  wired into `PageCurlView`, but no rendered frame has been through it — that
  needs the example app running on a device.
- **Anything at run time.** The Android library links and packages, but no
  code in it has executed on a device or emulator.
- **The podspec.** Syntax-valid and the xcframework it points at is built, but
  no `pod install` has been run against it.

## Not started

- **Example reader UI.** No document selector, TOC, search, bookmarks,
  text-size controls, or password prompt.
- **Design artifacts.** `docs/design/` does not exist — no research brief, no
  Mobbin reference sets, no tokens, no copy, no handoff specs, no accessibility
  audit, no critique.
- **CI.** No workflow for typecheck, native tests, Android or iOS builds, or a
  packed-package smoke test.
- **`npm pack` verification** and clean-consumer installs.
- **Device performance measurement.** No first-page latency, frame times, or
  memory figures on named hardware. Nothing has run on a device.

## Known limitations, stated rather than hidden

- **`progressionDirection` is hardcoded `ltr`** in `MuPDFSource`. MuPDF handles
  RTL text internally, but the engine does not yet read the spine's
  `page-progression-direction`, so an RTL-bound book pages the wrong way.
- **`ReflowablePaginator`'s character-count estimator is still live.** The brief
  asks for it to leave the production EPUB path. `MuPDFSource` does not use it,
  but nothing has removed it, and any caller still constructing a
  `ReflowablePaginator` gets the estimate.
- **`comic.epub` is fixed-layout**, so the repagination tests take their
  fixed-layout branch. A reflowable fixture is needed before the EPUB pagination
  claims mean much.
- **`renderPage` rasterises twice**, once for the encoded form and once for raw.
  `RenderedPage` exists partly to make that measurable before optimising.
- **Page boxes are prefetched, bounded at 64** (`MuPDFSource.prefetchPageBoxes`).
  `PageSource.getPageBox` is synchronous and the engine's is not. Past the
  window, a mixed-size PDF reports the first page's box until
  `refreshPageBox` resolves.

## Notes from building this

- The **release tarball pre-generates only the urw base-14 fonts**. Every other
  family ships as raw `.cff`/`.otf`/`.ttf` and upstream's Makefile converts them
  with `scripts/hexdump.sh` during a build; our CMake does the same at configure
  time. An earlier commit claimed all 183 were pre-generated — that was measured
  on a tree polluted by having run MuPDF's C++ binding generator, which
  triggered a build that produced them.
- **CMake 3.22 (what Android Studio ships) has no `DOWNLOAD_EXTRACT_TIMESTAMP`.**
  It does not reject the unknown keyword; it appends it to the preceding
  `URL_HASH`, which then fails to parse as `ALGO=hex`. The error names the hash
  and is nothing to do with the hash.
- **`fz_caught` does not clear `ctx->error.errcode`.** Leaving it set makes the
  next `fz_throw` print `UNHANDLED EXCEPTION!` and report the stale error.
  `fz_convert_error` is the call fitz documents for language bindings; it
  returns code and message *and* clears.
- `FZ_ERROR_MEMORY` does not exist in 1.28.4. Allocation failure arrives as
  `FZ_ERROR_SYSTEM` or `FZ_ERROR_LIMIT`.
- The context-global `fz_set_user_css` / `fz_set_use_document_css` are marked
  deprecated in `CHANGES` for 1.28.0 but carry no deprecation attribute in the
  headers, so using them compiles silently. `fz_style_document` is what this
  engine uses.
- MuPDF warns `unknown epub version: 3.0` on our EPUB fixture.
